# 江苏文化传承与创新平台可行性研究报告

> 文档版本：1.0
> 编制日期：2026 年 11 月 16 日
> 项目阶段：现有系统完善与试点上线可行性评估
> 依据：仓库当前代码、`README.md`、`docs/product/PRD.md`、`docs/planning/项目规划.md` 及 `apps/api/README.md`。实际部署和业务效果仍须在目标环境验证。

## 1. 项目背景

江苏拥有丰富的地域文化、非物质文化遗产、传统艺术和历史人物资料。相关信息分散在不同网站与资料库中，普通用户难以通过统一入口按城市或主题浏览，也缺少展示个人文化创作的便捷渠道。本项目拟建设面向公众和内容创作者的“江苏文化传承与创新平台”，支持文化资源探索、文化动态浏览、作品发布与管理。

本仓库已形成前后端分离的实现：`apps/web` 为 Vue 3 + Vite 前端，`apps/api` 为 Node.js + Hono API，数据、认证和图片存储使用 Supabase。原 Spring Boot 代码保留在 `legacy/spring-backend`，不属于当前运行方案。本报告评估的是**基于现有代码完成数据准备、质量改进和试点上线**的可行性，而非从零开发全部功能。

## 2. 建设目标与范围

### 2.1 建设目标

1. 为游客提供十三市文化入口，以及非遗、传统艺术、历史人物和文化动态的浏览与检索能力。
2. 为注册用户提供个人资料、文化作品上传与管理、收藏及互动能力。
3. 为管理员提供文化内容维护、发布或撤回、举报处理和基础统计能力。
4. 在试点环境完成“游客浏览—注册登录—作品发布—管理员发布内容”四条主流程验收，并形成可追溯的内容来源与授权记录。

### 2.2 本次评估范围

| 范围 | 内容 |
| --- | --- |
| 包含 | 现有前端和 API 的集成；Supabase 三份迁移执行；基础文化内容导入与复核；账号和管理员权限配置；作品图片、新闻正文、举报和限流等现有能力的目标环境验证；移动端适配与上线文档 |
| 条件性包含 | 地图漫游需提供有使用权的地图样式及瓦片服务；AI 生图需配置服务密钥、额度和预算，且须通过单独验收 |
| 不包含 | 原生移动应用、门禁或线下设备、第三方登录、自动内容审核、权威地理测绘、AI 文本大模型生成及大规模商业化运营 |

### 2.3 成功判据

试点上线前应同时满足：

- 四条主流程在目标环境各完成至少 1 次端到端验收，关键缺陷为 0。
- 所有公开展示的试点文化资料均有来源、复核人及素材使用依据；演示资料不得以权威事实发布。
- 普通用户不能调用管理员写接口，不能读取他人的私有作品；通过权限测试验证。
- 作品上传仅接受 JPG、PNG、WebP，单文件不超过 5 MB；上传失败、保存失败及重试均有明确反馈。
- 项目根目录的 `npm run build` 与 `npm test` 通过；部署、备份与回退步骤完成演练。

## 3. 备选方案分析

| 方案 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| A：沿用当前 Vue/Hono/Supabase 架构 | 复用现有页面、接口、迁移与测试；开发量较小；适合试点 | 依赖 Supabase 与部署平台；需核对服务额度和数据治理 | 推荐 |
| B：恢复旧 Spring Boot/MySQL 架构 | 可参考历史代码与文档 | 需要重新同步前端接口、权限、作品存储和近期功能，迁移成本高 | 不推荐作为本次试点路线 |
| C：仅保留静态展示站点 | 上线快、运维简单 | 无法满足注册、作品发布和内容管理目标 | 不满足项目目标 |

选择方案 A。保留默认文化星图作为城市探索入口；地图漫游作为可选模式，避免将第三方地图服务作为核心浏览流程的前置条件。

## 4. 技术可行性

### 4.1 总体方案

```text
浏览器（桌面/移动端）
        ↓ HTTPS
Vue 3 + Vite 前端
        ↓ /api
Node.js + Hono API（Node/Vercel/Cloudflare Workers 适配）
        ├─ Supabase Auth：用户认证
        ├─ Supabase PostgreSQL：文化内容、作品、互动与操作记录
        ├─ Supabase Storage：作品图片
        ├─ Upstash Redis：可选缓存；多实例限流时需要持久化共享计数
        └─ 火山引擎图像服务：可选 AI 生图
```

前端已具备城市文化星图、文化资源页面、图库、个人中心及内容编辑入口。API 已实现认证、文化内容、作品、收藏、评论、搜索、举报、管理员内容管理和基础统计等接口。作品图片私有访问、新闻 HTML 清洗、接口限流和 AI 每日额度已有代码支撑。上述能力是否在目标环境可用，取决于三份数据库迁移、环境变量、业务数据、管理员账号及外部服务配置；不能仅凭代码存在认定上线完成。

### 4.2 关键技术问题及处理方式

| 问题 | 处理方式 | 验证方法 |
| --- | --- | --- |
| MySQL 旧数据迁至 PostgreSQL | 按 `categories/cities → content → profiles → works/comments/collections` 的依赖顺序导出、清洗和导入；使用现有 SQL 迁移建立目标结构 | 对比导入前后记录数，抽查关联关系与中文文本 |
| 私有作品图片访问 | Storage bucket 设为私有，由 API 根据身份签发短期访问链接 | 未授权访问失败；作者和管理员按权限访问成功 |
| 富文本安全 | 新闻正文写入和读取时按允许标签清洗 | 使用脚本、事件属性等测试样例验证不可执行 |
| 多实例接口限流 | 试点多实例部署时配置 Upstash Redis；未配置时仅作为单实例限流 | 并发请求跨实例验证计数一致性 |
| 外部地图或 AI 服务不可用 | 默认文化星图继续可用；AI 生图显示明确错误和额度信息 | 停用外部配置后检查核心浏览链路 |

**判断：** 当前技术栈能够支撑试点目标。需要补齐的是部署配置、数据与端到端验收，而非重新选型。

## 6. 运行、法律与社会可行性

**运行条件。** 需指定业务负责人、内容复核人、管理员账号管理人和技术运维人；明确文化资料更新、用户举报响应和故障处理流程。现有代码可支持试点，但正式开放前必须准备真实内容、执行迁移并完成四条主流程验收。

**内容与素材。** 城市、非遗、人物、新闻和图片应记录来源、使用依据、复核时间和责任人。用户上传作品应提示其确认上传权利，并设置举报和下架处理流程。首页等现存演示资料应逐项核验，不能直接作为已认证文化信息对外发布。

**个人信息。** 用户资料、搜索历史和私有作品应按最小必要原则处理。服务端密钥仅保存在服务端环境变量中；管理员角色仅由可信部署者分配和撤销。正式上线前应由项目责任方核对适用的隐私告知、数据保存期限和第三方服务条款。

## 7. 主要风险与应对

| 风险 | 概率/影响 | 应对措施 | 责任建议 |
| --- | --- | --- | --- |
| 内容来源或图片授权不明 | 中/高 | 建立来源与授权台账；无法核验的内容保持草稿或移除 | 内容负责人 |
| 目标环境未执行第三份迁移 | 中/高 | 发布清单列出 `001`、`002`、`003`；部署后核验表、策略与私有 bucket | 后端开发 |
| Supabase、部署平台或 Redis 限额不足 | 中/中 | 上线前核对套餐和峰值；设置监控、预算告警及降级策略 | 运维人员 |
| 私有图片旧公开链接已被缓存 | 中/中 | 新链接改为签名访问；检查历史公开链接和外部引用，记录无法撤回的存量风险 | 后端开发 |
| AI 生图费用失控或服务不可用 | 中/中 | 保持登录校验和每日额度；设置预算上限；失败时不影响文化浏览 | 项目负责人 |
| 管理员误操作或权限滥用 | 低/高 | 角色最小化、操作日志、发布与撤回检查、定期审计 | 管理员负责人 |
| 静态演示数据与真实 API 数据混用 | 中/高 | 逐页标注数据来源，按 PRD 核查页面和接口，清除成功假象 | 前端开发、内容负责人 |

## 8. 资源需求与进度计划

### 8.1 资源需求

- **人员：** 项目负责人、前端开发、后端开发、测试、内容编辑各 1 名；项目负责人和测试按兼职投入估算。
- **技术环境：** Node.js 20+、前端静态托管、Hono API 运行环境、Supabase 项目、数据库备份和日志监控；多实例限流需共享 Redis。
- **外部资料：** 经确认的城市与文化内容、可用图片及授权记录、管理员账号、试点用户与验收样例。
- **可选服务：** 有授权的地图样式及瓦片服务、AI 图像服务密钥与预算。

### 8.2 八周计划

| 周次 | 工作内容 | 交付与退出条件 |
| --- | --- | --- |
| 第 1 周 | 逐页盘点现状、确认试点范围与验收口径 | 页面能力清单、需求基线 |
| 第 2 周 | 准备 Supabase、执行三份迁移、配置环境和管理员 | 目标环境健康检查、迁移记录 |
| 第 3—4 周 | 导入并核验文化内容；修正页面数据来源、空状态与错误提示 | 内容来源台账、可浏览的试点数据 |
| 第 5 周 | 验证作品上传、私有访问、内容发布、举报和 AI 条件性能力 | 功能测试记录与缺陷清单 |
| 第 6 周 | 完成权限、安全、并发、移动端和故障恢复测试 | 测试报告、已修复关键缺陷 |
| 第 7 周 | 邀请试点用户验收，修复问题并核算实际服务费用 | 用户验收记录、费用复核 |
| 第 8 周 | 试点发布、培训、备份与回退演练 | 部署手册、运维交接与上线记录 |

进度以环境、数据和内容授权按时到位为前提。地图漫游与 AI 生图未达到条件时，不应阻塞不依赖它们的核心试点流程，但对外说明须准确标注其状态。

## 9. 验收与决策建议

**建议结论：有条件可行。** 现有代码与架构能够支撑江苏文化内容浏览、用户作品发布和管理员维护的试点。项目进入公开试点前，须完成数据库迁移、真实内容与素材核验、管理员权限配置、目标环境主流程测试及备份回退演练。若内容授权或目标环境无法落实，应推迟公开发布，而不是用演示资料代替正式数据。

**决策检查点：** 第 2 周确认技术环境；第 4 周确认内容质量；第 7 周根据验收结果和实际服务报价决定是否发布。
